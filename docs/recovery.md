# 백업·중단·업그레이드·복구

## 백업

작품을 다루는 호스트와 MCP 서버를 중지한 뒤 작품 폴더 전체를 복사한다.
`work.yaml`, `tree/`, `entities/`, `sources/`, `assets/`, `checks/`와
`.folio/`를 포함한다. 실제 존재하는 폴더만 복사하면 된다.
본문만 복사하면 영수증·사건·결정·실행 상태를 복원할 수 없다.
백업은 원래 폴더와 다른 위치에 두고, 복사본을 열어 확인한다.
새 폴더에 복원한 사본을 `linivera-doctor <copy> --json`으로 먼저 검사하고,
같은 Linivera 버전으로 재연결해 변경·승인 이력을 조회한다.
자세한 수용 순서는 [진단과 운영 안내](operations.md)를 따른다.

`.folio/index.db`는 파생 색인이다. 기록장 대신 사용할 수 없으며
사용처·사건 조회 과정에서 다시 만든다.

## 대화나 프로세스가 멈췄을 때

1. 같은 작품 폴더로 MCP 서버를 다시 연결한다.
2. `folio_status`에서 `ledger`, `warnings`, `activeRun`, `pending`, `drift`를 확인한다.
3. `pending`이 모델 요청이면 그 요청에 답하고, 작가 질문이면 작가의 결정을 받는다.
   이미 보낸 답이나 승인 기록을 추측해서 내부 파일에 쓰지 않는다.
4. 커밋 중 중단됐으면 같은 `folio_run`으로 이어간다. 엔진은 기록된 영수증으로
   중복 커밋을 막고 완료한다. 새 작품으로 초기화하지 않는다.

## 엔진이나 팩 업그레이드

진행 중인 작업을 가능한 한 끝내고, 서버를 중지하고, 작품 전체를 백업한다.
소스를 업데이트한 뒤 `npm ci`로 설치하고 MCP 서버를 **재시작**한다.
내장 팩 코드는 서버 시작 시 로드된다. 실행 중인 서버의 모듈이 자동 교체되지는 않는다.

이번 digest 보완은 결정론 검사 구현을 검사별 hash에 포함한다.
예전 기록은 보존하지만, 기존 커밋에 재검사 표시가 새로 나타날 수 있다.
`folio_status.recheck`를 확인하고 원하는 노드를
`folio_run { root, node, mode: "recheck" }`로 검사한다.
재검사는 본문을 자동 수정하지 않는다.

`ANSWER_STALE`이면 `folio_run`으로 새 요청을 받는다.
커밋 영수증이 이미 기록된 상태에서 `LOCK_PIPELINE_MISMATCH`가 발생하면
호환되는 옛 소스·설정으로 복귀해 완료하거나, 작가가 이유를 남겨 실행을 포기한 뒤
노드를 다시 실행한다. 이 과정에서 기록장을 지우거나 고치지 않는다.

## 자동 복구가 거부됐을 때

| 표시 | 대응 |
|---|---|
| `TX_INTERRUPTED`, `valid: true` | 쓰기가 중단됐다. 다음 쓰기 도구 호출이 안전한 복구를 시도한다. 상태 조회는 복구를 수행하지 않는다 |
| `TX_CONFLICT` | 중단 후 파일이 바뀌었다. 모든 쓰기를 중지하고 작품 전체와 `.folio/tx`를 보존한다. `details.paths`의 파일을 백업과 비교한다 |
| `TX_JOURNAL_INVALID` | 복구 기록이 손상됐거나 옛 형식이다. 원고를 보존한 채 정상 백업과 비교한다 |
| `LEDGER_TAMPERED` 또는 `ledger.*.ok: false` | 기록장 손상·변경이 감지됐다. hash를 재계산하거나 마지막 줄을 지워 통과시키지 않는다. 정상 백업을 별도 폴더에서 확인한다 |
| `WORK_LOCKED` | 다른 쓰기 호출이 진행 중인지 확인한다. 실행 중인 프로세스의 잠금 파일을 지우지 않는다 |

`TX_CONFLICT`·`TX_JOURNAL_INVALID`는 작가가 원고와 백업을 비교해 보존할 내용을
결정해야 한다. 수동 해결이 끝났고 별도 백업이 있을 때만 작가가 `.folio/tx`를
제거해 쓰기 차단을 해제한다. 호스트가 자동으로 어느 내용을 고르거나 제거하지 않는다.
자세한 도구 흐름은 [등장 위치 안내](../skill/folio/references/occurrences.md)를 참고한다.

전원 손실·파일 시스템 손상에 대한 내구성 보장은 없다. SIGKILL 재개 테스트는
전원 손실 테스트와 다르다. `linivera-doctor`는 읽기 전용 검사이며 손상된
파일을 자동 복구하지 않는다. 손상 재현은 실제 원고 대신 합성 입력으로 공유한다.

## 불변 객체와 작품 잠금

불변 객체(요청·결과·영수증·리소스·투영)는 같은 디렉터리의 고유 임시 파일을
완전히 쓴 뒤 배타적 hard link로 게시한다. 게시 전 프로세스 중단이나 디스크 부족은
최종 이름에 반쪽 파일을 남기지 않는다. 같은 요청 키로 다시 호출해 완료한다.
`.immutable-<UUID>.tmp` 이름의 일반 고아 파일은 권위 있는 객체나 세대 목록에
포함하지 않고 그대로 보존한다. 조회·doctor는 이를 삭제하거나 복구하지 않는다.
알 수 없는 이름, 심볼릭 링크, 특수 파일 및 손상된 최종 세대는 계속 오류로 거부한다.
기존 최종 객체의 바이트가 다르면 교체하거나 삭제하지 않고 무결성 오류로 거부한다.
공유 불변 객체 하나의 상한은 8MiB이며, 내부 JSON 객체에도 같은 상한이 적용된다.

관리 이미지 사본도 `assets/files/`의 고유 `.asset-<UUID>.tmp`에 전체 바이트를
쓴 뒤 배타적 hard link로 게시하고, 이후에만 자산 판본을 기록한다. 부분 쓰기나
프로세스 중단 뒤 같은 ID·같은 입력으로 `folio_assets put`을 다시 호출할 수 있다.
중단된 임시 사본은 정본 판본이 아니며, 재시도가 이전 고아 파일을 삭제하지 않는다.
기존 최종 사본의 바이트 불일치·심볼릭 링크는 거부한다. 관리 이미지의 상한은
별도로 20MiB를 유지한다. 이 게시 방식도 전원 손실 내구성을 약속하지 않는다.

`.folio/runs/.lock`의 기존 PID·시각·token 형식은 유지한다. 모든 새 버전 쓰기 호출은
획득·죽은 PID 복구·해제 동안만 `.folio/runs/.lock-gate.sqlite`에서
SQLite `BEGIN IMMEDIATE` 게이트를 잡는다. 긴 실행 콜백 동안은 게이트를 잡지 않는다.
다른 호출의 게이트 점유는 이벤트 루프를 막지 않고 최대 약 500ms 재시도한 뒤
`WORK_LOCKED`로 획득을 거부한다. 이미 잠금을 가진 소유자의 해제는 시간 초과로
포기하지 않고 게이트가 풀릴 때까지 비동기로 기다린다. 다른 게이트 소유자가
중지된 상태면 원래 호출 완료도 재개·종료까지 기다릴 수 있다. 살아 있는 잠금을
강제로 지우지 않는다. 실제 프로세스 종료는 OS 게이트를 해제한다.
살아 있거나 중지된 PID의 파일 잠금은 시계가 달라도 보호한다.

`WORK_LOCK_GATE_FAILED`이면 서버 쓰기를 중지하고 작품 전체, `.lock`, 게이트 DB와
동반 journal/WAL/SHM 파일을 보존해 조사한다. 손상된 게이트는 자동 삭제·재생성하지
않는다. 게이트와 동반 파일의 심볼릭 링크도 거부한다. 백업·이전은 모든 서버를
중지하고 수행한다. 한 작품의 모든 쓰기 프로세스는 같은 새 버전을 사용해야 한다.
게이트를 모르는 옛 버전과의 혼합 쓰기는 보호하지 않는다. 이 프로토콜은 fsync나
전원 손실 내구성을 약속하지 않는다.
