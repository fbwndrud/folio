# 집필용 작품 데이터베이스 설계 초안

작성일: 2026-10-07. 상태: 검토용 설계 초안이며 구현 승인을 뜻하지 않는다.
승인된 착수 계획서 아티팩트와 기존 동적 추적 설계의 정본 지위는 유지한다.

2026-10-08 범용 제품 방향은 [AI 작업 데이터 관리 설계](2026-10-08-general-ai-work-data-design.md)로 갱신했다.
아래 내용은 집필 분야의 적용 설계이며 Folio 전체의 타깃이나 파이프라인을 제한하지 않는다.
이 문서의 단계 순서보다 [범용 기반 이식 계획](2026-10-08-general-data-port-plan.md)을 우선 검토한다.

집필 분야의 목적은 새로 쓰거나 가져온 작품을 근거가 연결된 데이터로 관리하고,
사람과 호스트 AI가 작품별 규칙·검색·요약·시각화를 함께 사용하는 것이다.
초기 저장 구조는 작품 폴더의 원문·기록장과 하나의 SQLite 조회 DB를 중심으로 확장한다.
관계형 조회, 유연한 객체, 키워드 검색, 의미 검색, 위키는 각자의 역할을 가진다.

## 1 사용자에게 제공하는 작업

- 새 작품: 인터뷰 → 추적 계획 결정 → 집필·추출 → 후보 검토 → 확정 → 요약·검색 갱신.
- 기존 작품: 원본 보관 → 문서 구조 확인 → 추적 계획 결정 → 분할 추출 → 후보 검토 → 데이터화.
- 조회: 인물 카드와 해당 시점의 상태를 먼저 읽고, 관계·변화·근거 문장을 펼쳐 본다.
- 수정: 설정·관찰·규칙 변경 후 영향을 받은 기록과 오래된 요약을 확인한다.

AI는 추출·요약·임베딩·의미 검토를 호스트에서 수행한다. Folio는 입력과 산출물을
검증·기록·조회하며 `core/`와 팩에서 모델·네트워크를 호출하지 않는다.
자동 관리의 범위는 실제 위임으로 정하고 불명확한 해석과 충돌을 그대로 드러낸다.

## 2 저장 기술 선택

| 필요 | 초기 선택 | 이유와 범위 |
|---|---|---|
| 읽고 수정하는 원고와 입력 자료 | 파일, 원문 버전 사본 | 기존 집필 방식과 원본 보존을 유지한다 |
| 승인·확정·변경 이력 | 기존 추가만 되는 기록장 | 기존 영수증·hash·위임 잠금을 보존한다 |
| 대상·관찰·근거·관계 조회 | 기존 SQLite 확장 | ID와 근거를 공통 열로 연결하고 조건 조회한다 |
| 작품별 유연한 속성 | 검증된 JSON과 타입 열 | 장르마다 새 테이블을 만들지 않는다 |
| 키워드 검색 | SQLite FTS5 및 짧은 검색어 보완 | 이름·별칭·본문·요약을 같은 작품 범위에서 찾는다 |
| 의미 검색 | 호스트 임베딩, 보관된 벡터, 초기 정확 거리 계산 | 임베딩 제공자를 고정하지 않는다 |
| 위키와 인물 카드 | 근거·범위가 붙은 파생 문서와 구조화 상태 | 읽기 편한 요약을 앞에 놓되 원문에 연결한다 |
| 관계도·시간선 | 같은 조회 데이터의 화면 | 그림을 별도 사실 저장소로 만들지 않는다 |

SQLite는 JSON 함수와 FTS5를 제공한다. 따라서 초기에는 관계형 조회·유연한 속성·전문 검색을
하나의 저장 엔진 안에서 구성할 수 있다. [JSON 문서](https://www.sqlite.org/json1.html),
[FTS5 문서](https://www.sqlite.org/fts5.html)를 근거로 한 선택이다.
한국어 형태소 분석과 벡터 가속이 자동으로 제공된다는 뜻은 아니다.

작품 단위 로컬 저장과 낮은 쓰기 동시성을 초기 조건으로 삼는다.
여러 기기의 동시 편집·공유 서버가 실제 제품 요구가 되면 PostgreSQL 중심의 서버 설계를
별도로 검토한다. SQLite 파일을 여러 기기에서 직접 공유하며 쓰는 방식은 선택하지 않는다.
[SQLite 적용 조건](https://www.sqlite.org/whentouse.html).

문서 DB·그래프 DB·검색 서버·벡터 서버의 동시 도입은 현재 요구와 실측으로 정당화되지 않았다.
벡터 가속은 작품 크기·지연·메모리를 측정한 뒤 확장 여부를 결정한다.

## 3 정본과 파생 데이터

| 층 | 보관할 것 | 변경과 재구성 |
|---|---|---|
| 원문과 결정 | 원고 버전, 가져온 원본, 계획, 승인, 영수증, 확정 관찰 | 기존 기록을 덮어써 승인 이력을 바꾸지 않는다 |
| 보관된 파생 산출물 | 위키 버전, 임베딩 결과, 입력 결속 manifest | 산출물 bytes와 hash를 보관하고 새 결과는 새 버전으로 추가한다 |
| 조회 투영 | SQLite 표, FTS 색인, 현재 상태 카드, 검색 목록 | 원문·기록·보관된 산출물로 모델 호출 없이 다시 만든다 |

원고 파일은 편집할 수 있다. 확정·가져오기 때의 원문 버전은 별도로 보존해 예전 근거가
어느 문장을 가리켰는지 재현한다. 손으로 편집한 내용은 기존 승인과 동일한 버전이 아니다.
원본 bytes, 변환 텍스트, 확정 원고는 각각 식별하고 hash를 따로 둔다.

위키와 임베딩은 원작의 사실을 확정하는 정본이 아니다. 다만 생성 결과를 보관해야
네트워크와 모델 없이 같은 조회 DB를 복구할 수 있다. DB 삭제와 산출물 삭제를 구분한다.
산출물을 분실하면 재생성이 필요한 상태를 알리고 위키·벡터 부분의 완전한 복구를 주장하지 않는다.

## 4 조회 데이터 모델

다음은 조회용 표의 역할 초안이다. 기존 표를 재사용할 부분과 신규 표를 구현 계획에서 확정한다.
공통 식별·상태·근거 열은 정형화하고 장르별 확장 정보는 검증된 JSON으로 둔다.

| 모델 | 중요한 정보 |
|---|---|
| DocumentVersion | documentId, revisionId, 원문 hash, 구조·순서, 보관 위치, 원본 형식 |
| Chunk | chunkId, revisionId, 원문 위치, 텍스트 hash, 분할 방식 버전 |
| Entity | entityId, kind, 이름·별칭, 정의 버전, 추가 속성 |
| Criterion | criterionId, 의미 버전, 값 타입, 적용 범위, fixed/state/relation/note |
| Observation | observationId, 대상·기준, 타입 값, explicit/attributed/inferred, 관점, 시간·공개 범위, 근거 |
| Relation | observationId, 출발·도착 대상, 관계 기준, 시점·관점·상태 |
| Evidence | 원문 버전·node/chunk, 정확한 인용과 위치, 당시 hash |
| Decision | 결정·위임·출처, 입력 결속, 기록 순서 |
| Coverage | 원문·기준·대상 목록별 확인/미확인/차단/변경 상태 |
| WikiArtifact | pageId, 대상, 범위, 입력 의미 digest, 산출물 hash, 생성·검토 상태 |
| EmbeddingArtifact | chunkId, 텍스트 hash, profileId, 차원, metric, 벡터 hash |
| ProjectionManifest | 스키마·분할 버전, 원문 목록, 기록장 heads, 산출물 heads, generationId |

관계 표는 검증된 entity/entity-list 관찰에서 만든다. 관계도만을 위한 별도 진실을 만들지 않는다.
주장과 추론은 같은 관계도에서도 구분하고 클릭하면 해당 관찰과 근거로 이동한다.
기존 1개 근거 규약을 여러 근거 규약으로 확장할 경우 버전과 호환 처리를 먼저 설계한다.

## 5 최신 상태의 의미

작품의 최신 상태를 단순한 기록장 마지막 seq로 결정하면 회상·추측·소급 수정에서 틀린다.
조회 범위를 다음 축으로 나눈다.

- 원고 판본: 어떤 확정 원문 버전들을 읽는가.
- 공개 범위: 어느 장면까지 읽은 독자에게 공개된 정보인가.
- 작품 속 시점: 시간선이 선언되고 검증된 경우 어떤 시점인가.
- 관점: 작가가 정한 사실인가, 누구의 주장인가, 추론인가.
- 기록 시점: 언제 추출·수정·승인된 기록인가.

기본 카드는 선택한 장면까지 공개된 정보로 구성한다. 작품 속 시간선이 없으면 읽기 순서
기준이라고 표시하고 실제 연대기 순서를 계산했다고 말하지 않는다.
현재 구현의 시간·경로 표지는 상태 계산기가 아니다. 이 제약은 확장 구현 전까지 유지한다.
상태 전환의 순서나 유효 구간을 알 수 없으면 복수 관찰과 미확정 표지를 보여 준다.
기록장 마지막 값이나 AI가 부여한 신뢰도만으로 하나의 현재 값을 선택하지 않는다.

예: 뒤 장에 어린 시절의 마라가 등장해도 현재 마라의 나이가 그 값으로 덮이지 않는다.
한 인물의 주장과 다른 인물의 반박은 함께 남기며 서로 다른 값을 임의로 하나로 합치지 않는다.
분기형 작품은 pathId를 보관하는 것과 경로별 도달 상태를 계산하는 것을 구분한다.
경로 해결기 전에는 복수 경로가 섞인 자료로 확정 상태 카드를 만들지 않는다.

## 6 위키와 중요한 정보를 앞에 놓는 방법

LLM Wiki 구현 사례는 원자료, 생성된 위키, 구조·작업 규칙을 나누고 요약과 개념 페이지를
유지한다. 이 분리 방식을 참고하되 작품에는 시점·관점·승인·근거 규약을 추가한다.
[참고 구현의 스키마](https://github.com/danvega/karpathy-wiki/blob/master/SCHEMA.md).

조회·집필 요청의 앞부분은 다음 순서로 만든다.

1. 사용자가 정한 목표·고정 사실·적용 기준.
2. 해당 범위의 구조화된 인물·대상 상태, 충돌, 아직 모르는 부분.
3. 입력이 현재 범위와 일치하는 위키 요약과 관련 페이지 링크.
4. 조건·키워드·의미 검색으로 찾은 근거 문장과 추가 관찰.

중요도는 사용자 우선순위·현재 장면과의 관련성·미해결 충돌을 먼저 적용한다.
AI가 임의로 중요한 정보를 확정하거나 요약이 원문을 대체하지 않는다.
사용자에게는 카드·읽기 범위·미확인 표지를 보여 주고 내부 digest 등은 펼쳐 볼 때 제공한다.
작가의 집필 문맥과 독자의 열람 문맥을 구분한다. 작가가 알고 있는 미래 설정을
독자 카드·검색·관계도에 노출하지 않으며 요약·벡터도 동일한 공개 범위로 제한한다.

위키의 생성과 검토는 다음 규약을 따른다.

- 입력 문서·계획·대상·관찰의 의미 digest와 범위가 요청에 결속된다.
- 요약 문장 또는 단락에는 원문과 관찰로 돌아가는 근거 참조가 있다.
- 기계 검증은 참조의 존재·hash·범위를 검사한다. 요약의 의미적 정확성은 호스트 검토다.
- 생성과 검토가 같은 호스트이면 자기검토로 표시한다.
- 미검토 요약은 그 상태로 표시하며 고정 사실이나 확정 관찰을 추가할 수 없다.
- 입력이 바뀌면 이전 요약은 오래된 상태가 된다. 기본 문맥에서 제외하고 갱신 필요를 알린다.
- 수동 수정은 사용자 노트·결정으로 출처를 남긴다. 파생 요약을 고쳐 원작의 사실을 바꾸지 않는다.

위키 갱신 권한은 기존 네 추적 위임과 별개로 설계한다. 기존 승인에서 새 권한을 추론하지 않는다.
문맥 길이 제한 시 근거 링크와 미확인 정보를 남기고 잘린 범위를 표시한다.
위키가 없거나 오래되어도 구조화된 상태와 원문 검색을 사용할 수 있어야 한다.

## 7 키워드와 의미 검색

검색 결과는 항상 같은 원문 버전·기록 snapshot에서 만들고 적용 범위와 사실 상태로 먼저 걸러낸다.
반환값에는 대상/문서/원문 위치, 검색 방식, 근거, 상태, generationId, incomplete 여부를 둔다.
역사 검색은 별도 선택이며 오래된 정보가 현재 사실처럼 섞이지 않는다.

키워드는 이름·별칭 정확 검색, 일반 FTS, 부분 문자열 보완으로 구성한다.
한국어는 기본 Unicode 토큰 검색만으로 조사를 제거하지 않는다. trigram의 MATCH도 세 글자
미만 검색어에는 결과가 없다. 짧은 이름과 검색어는 구조화 별칭 조회 및 범위가 제한된
문자열 검색으로 보완한다. [FTS5 tokenizer 문서](https://www.sqlite.org/fts5.html#tokenizers).
제한에 걸리면 검색하지 않은 범위와 이어 읽기 cursor를 반환하고 결과 없음으로 단정하지 않는다.
FTS 문법은 사용자 문자열과 구분하고 SQL은 parameter binding으로 전달한다.

임베딩은 호스트가 요청된 원문 chunk의 hash와 profile에 맞춰 생성해 제출한다.
profile에는 model/revision 또는 사용자 선언 식별자, 차원, 정규화 정책, metric을 포함한다.
검색 질문의 벡터도 같은 profile이어야 하며 차원만 같다는 이유로 다른 모델 벡터를 섞지 않는다.
유한 수·크기·차원·hash·현재 버전·위임을 검사하고 cosine의 영벡터 같은 무효 입력은 거부한다.
host의 profile 표기는 기계적인 모델 실행 인증이 아니므로 생성 출처도 함께 보관한다.

초기에는 필터된 벡터에 정확 거리 계산을 적용한다. chunk 수·차원·메모리·지연 예산은
합성 규모 시험으로 정하고 그 예산을 넘으면 불완전 상태를 반환한다.
ANN이나 native extension은 플랫폼·지원 Node·라이선스·정확도·설치본 검증 뒤 별도 결정한다.
벡터 검색이 비활성·미보충이어도 키워드·조건 조회는 동작한다.
혼합 검색은 각 검색의 순위를 결합하고 서로 다른 점수를 그대로 더하지 않는다.
유사도는 발견 후보를 정렬하는 값이며 사실·동일 인물·모순 여부의 자동 승인 기준이 아니다.

## 8 기존 작품 가져오기

첫 단계는 UTF-8 텍스트·Markdown으로 제한한다. PDF·EPUB·DOCX는 후속 변환 입력으로 확장한다.
변환은 원본 hash와 변환 도구·버전, 텍스트, 가능한 위치 대응을 남긴다.
페이지/문단 대응이 불명확하면 해당 위치 정확도와 미확인 범위를 명시한다.

원본을 보관한 뒤 구조와 추적 계획을 사용자가 결정한다. extraction은 원문 chunk를 기준으로
재개 가능한 작업으로 실행하고 처리 범위를 기록한다. 문서 내용은 입력 자료이며,
그 안의 명령문을 승인·위임·도구 실행 지시로 사용하지 않는다.
동일 이름은 동일 대상의 증거가 아니다. 자동 덮어쓰기·병합 대신 구분 후보를 만든다.

사용자가 추출 결과를 승인한 것은 원작자가 사실을 승인했다는 뜻이 아니다.
가져오기 결정과 저작 내 주장, 확정 원고의 채택을 구분한다.
현재 backfill은 이미 확정된 원고만 처리하므로 가져오기용 source receipt와 활성화 규약을
신규 설계한다. 기존 원고 commit 영수증을 위조해 가져온 문서를 끼워 넣지 않는다.
skip·중단·crash 뒤 승인되지 않은 추출 결과는 현재 관찰로 활성화하지 않는다.

## 9 동적 규칙과 확정 절차

작품별 대상 종류·추적 기준·보기 우선순위는 인터뷰와 실제 사용자 결정으로 설정한다.
AI는 위임 안에서 추가 후보를 만들 수 있다. 고정 값 변경·규칙 의미 변경·위임 확대는
기존 사용자 결정 규약을 유지한다. 위키·검색·화면에서 직접 정본을 우회 수정하지 않는다.

새 선언형 기준은 자동으로 실행 검사 코드가 되지 않는다. 기존 검사 관리 흐름을 재사용한다.
새 규칙 실행기가 필요하면 허용된 비교·타입·범위 연산을 가진 제한된 선언형 표현부터 설계한다.
임의 JavaScript·SQL·shell을 사용자 규칙이나 AI 생성 데이터에서 실행하지 않는다.
AI 의미 검토는 근거가 필요한 experimental/advisory로 시작하고 차단 수준 변경은 사용자 결정이다.
원문 hash, 영수증, hard 차단, append-only, 자기검토 표기, soft 비자동수정은 해제할 수 없다.

## 10 모듈과 작은 외부 인터페이스

| Module | 한 가지 책임 |
|---|---|
| DocumentHistory | 원문 버전과 chunk의 재현 가능한 위치 |
| KnowledgeProjection | 정본을 공통 구조·상태·근거 조회로 투영 |
| WikiArtifacts | 입력에 결속된 요약의 생성 요청·보관·오래됨 판정 |
| Search | 조건·키워드·벡터 검색과 근거가 있는 결과 결합 |
| Context | 장면·관점별 우선순위와 길이 예산에 맞춘 문맥 구성 |
| Import | 원본 구조 확인·분할 추출·승인·재개 |

호스트와 화면은 조회, 문맥 요청, 생성 작업의 제출·결정을 사용한다.
사용자에게 저장 엔진·색인 종류별 도구를 외우게 하지 않는다.
정확한 MCP 도구명과 schema는 단계별 구현 계획에서 확정하며 기존 공개 도구를 성급히 교체하지 않는다.
벡터 Adapter는 초기 구현 하나만 둔다. 실제 두 번째 구현 요구 전에 범용 plugin framework를 만들지 않는다.

## 11 현재 코드에서 이어가는 순서

| 단계 | 구현 결과 | 완료 검증 |
|---|---|---|
| 1 | 원문 버전·chunk·관찰·근거를 공통 조회로 묶기 | 전체 DB 삭제 후 조회 재구성, 기존 잠금·도구 회귀 |
| 2 | 정확·별칭·한국어 키워드 검색 | 한두 글자·조사·동명이인·부분 검색·범위 제한·입력 공격 |
| 3 | 범위별 상태 카드·위키·문맥 앞부분 | 회상·관점·스포일러·충돌·오래된 요약·잘린 문맥 |
| 4 | 기존 텍스트 작품 가져오기 | 원본 유지·분할 근거·skip·crash·중복 재시도·승인 출처 |
| 5 | 임베딩·혼합 검색 | 다른 profile·차원·오래된 원문 거부, 벡터 off·불완전 결과 |
| 6 | 작품 뷰어·관계도·변화 화면 | 동일 조회 결과, 근거 이동, 사실/주장 구분, 최신/과거 범위 |

현재 구현의 기반은 계획·대상·관찰·근거·위임·영수증·보충·coverage·stale·SQLite 일부 조회다.
전체 관찰/근거 SQL 투영, 위키, 검색, 원문 버전 보관, 가져오기, 작품 뷰어는 새 구현 범위다.
이 초안은 해당 기능이 구현되었거나 새 검색을 포함한 테스트가 통과했다고 주장하지 않는다.

조회 DB 재구성은 새 generation을 따로 만들고 입력 manifest 일치를 확인한 뒤 공개한다.
진행 중인 기존 조회 DB를 먼저 지우지 않는다. 작품 잠금과 입력 확인을 통해 두 snapshot을
섞지 않으며 실패한 재구성은 기존 조회를 유지한다. hash가 다른 정본은 기존 색인으로 숨기지 않는다.
증분 갱신 전에 전체 재구성이 같은 결과를 내는 기준 구현을 먼저 만든다.

## 12 설계 확인과 남은 결정

2026-10-07 로컬 macOS·Node 24.19.0·SQLite 3.53.3의 메모리 DB에서 JSON 추출,
FTS5 Unicode61·trigram 표 생성과 합성 문장 검색을 확인했다.
`마라는 붉은 외투를 입었다`에서 Unicode61 `외투`=0/`외투를`=1,
trigram `외투`=0/`외투를`=1이므로 한국어 보완을 초기 범위에 포함한다.
이는 저장 기술의 가능성과 제약 확인이며 제품의 검색 구현·검색 품질 검증은 아니다.

지원 Node·OS 전체의 capability 검사는 단계 2에 포함한다. 없는 기능은 명확히 알리고
기존 집필 흐름을 깨지 않는 상태로 남긴다. 실제 작품·생성 결과를 테스트 커밋에 넣지 않는다.
새 의존성·원문 보관 공간·검색 지연 예산·호스트 문맥 길이·새 위임은 단계별 계획에서 확정한다.
기존 추적 의미와 잠금을 변경하는 경우 별도 변경 규약과 실제 회귀 근거가 필요하다.
이번 설계의 핵심 비용은 원문 버전·산출물 보관 공간, 요약 갱신 비용, 범위별 상태 계산 복잡도다.

정본을 SQLite로 옮기는 전면 전환은 이번 선택에 포함하지 않는다.
서버형 협업 저장, 대규모 벡터 가속, 분기 경로 해결기, PDF/EPUB 출력은 각각의 실측·제품 요구로
후속 설계를 연다. 최종 제품 목적을 넓히면서 현재 검증된 저장·승인 기반을 단계적으로 확장한다.
