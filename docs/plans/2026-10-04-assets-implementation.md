# 제공자 독립 자산 관리 구현 계획

사용자가 지정한 설계 방향은 [공통 자산 관리 기준](2026-10-04-provider-neutral-assets.md)이다.
이미지 생성·편집·시각 검토는 호스트가 수행하고 Folio는 데이터와 작업 기록을 관리한다.
이 계획은 그 방향을 기존 원고 잠금·영수증·재검사에 연결하는 첫 구현이다.

## 완료할 사용자 흐름

작가가 그림을 요청한다 → 호스트가 설명서를 Folio에 등록한다 → 호스트가 자신의
이미지 도구를 사용한다 → 결과를 공통 형식으로 인계한다 → 호스트가 해당 결과를
검토해 기록한다 → 작가가 그 버전을 보고 결정한다 → Folio가 승인 기록과 사용 위치를 관리한다.
호스트에 생성 기능이 없으면 설명서만 남겨 둔다.

## 데이터와 식별자

- Folio 자산 `id`는 작품 안의 논리 ID다. 제공자의 `imageId`는 선택적인 `origin` 정보다.
- 관리 자산의 정본은 `.folio/ledger/assets.jsonl`의 hash 사슬 기록이다.
  설명서·결과 버전·검토·사용 위치·작가 결정을 추가만 한다. 실행 파일이나 YAML을
  고쳐 승인 상태를 만들지 않는다. 기존 YAML 자산은 읽기·참조 호환을 유지한다.
- 설명서나 결과 변경은 새 `version`이다. 검토는 version과 결과 contentHash에 묶고,
  승인은 최신 검토에 묶는다. 새 버전·새 검토·수정 요청에 옛 승인을 재사용하지 않는다.
- 호스트가 전달하는 `path`는 파일 하나다. Folio는 내용을 작품 안의 불변 사본으로 저장하고
  실제 바이트 hash를 계산한다. 원본 경로에 의존하지 않는다.
- `uri`는 다운로드하지 않는 외부 참조다. 호스트가 준 hash도 확인된 hash로 취급하지 않는다.
  참조만 있는 상태는 승인할 수 없다. 호스트가 파일을 확보한 뒤 새 버전으로 인계한다.
- 상태: `planned`, `reference_only`, `ready`, `reviewed`, `approved`, `needs_revision`,
  `content_changed`, `content_missing`. 바이트 확인과 호스트가 보고한 시각 검토를 구분한다.
- 사용 위치는 별도 연결 기록으로 관리해 커밋된 원고를 손으로 수정하지 않는다.
  기존 앞머리 assets와 본문의 `![[asset:id]]`도 함께 조회한다.
- 관리 설명서는 일괄 이름 바꾸기의 파일 쓰기 대상으로 삼지 않는다.
  해당 후보를 제외하고 `update`로 새 버전을 남긴다. 안정적인 엔티티 ID 연결은 유지한다.

## 공통 도구

`folio_assets` 하나에 다음 작업을 둔다. 모든 입력은 작업별로 추가 키를 거부한다.

| op | 입력의 핵심 | 결과/조건 |
|---|---|---|
| add | id, title?, brief | 설명서만 등록, 중복 ID 및 기존 YAML ID 충돌 거부 |
| update | id, expectedRev, title?, brief | 설명서 새 버전, 옛 검토·승인 미적용 |
| put | id, expectedRev, path 또는 uri, mediaType, origin?, contentHash? | 생성 결과 새 버전; path 바이트 검사, URI 미확인 |
| attach | id, expectedRev, nodeIds | 사용 위치 목록을 기록; 없는 노드 거부 |
| review | id, expectedRev, contentHash, checked, findings | 검토 영수증; 실제 파일이 현재 버전 hash와 같아야 함 |
| decide | id, expectedRev, reviewId, action, reason? / feedback? | 작가 승인 또는 수정 요청; 승인 불가 우회 불가 |
| list | 추가 인자 없음 | 자산 상태·미완료 요약 |
| get | id | 설명서·결과·검토·승인·사용 위치·추가만 되는 이력 |

쓰기 작업은 기존 작품 잠금 안에서 수행하고 원고 실행이 열린 동안 거부한다.
읽기는 잠금 안에서 현재 상태를 계산한다. optimistic expectedRev로 오래된 결정을 막는다.
assets 기능 토글은 도구 사용만 제어한다. 이미 기록된 자산의 무결성과 원고 참조 확인은
기능 토글·팩·검사 설정으로 해제하지 않는다.

## 검토와 잠금

- 등록 파일은 20MiB 이내의 일반 파일이어야 한다. 링크·디렉터리·FIFO·경로 탈출,
  assets 저장 폴더 및 내부 기록 폴더의 링크를 거부한다. 출력 사본은 덮어쓰지 않는다.
- 파일 변경·손실·미확인 URI는 승인 불가다. hash는 파일 내용 확인이며 시각적 사실 인증이 아니다.
- 검토는 고정 공통 목록을 모두 답해야 한다: `asset.fixed-facts`(hard),
  `asset.brief-fit`(block), `asset.quality`(advisory). severity는 Folio가 붙인다.
  호스트가 hard를 advisory로 낮추거나 목록을 빼서 승인할 수 없다.
- 검토자는 같은 호스트의 자기검토로 기록한다. 독립 검토 옵션을 받지 않는다.
- hard 지적은 이유가 있어도 승인 불가. block은 작가가 이유를 남겨야 승인할 수 있다.
  advisory는 기록·표시하고 자동 교체·재생성하지 않는다.
- 검토 후 파일 또는 설명서가 바뀌면 승인 불가. 잘못된 입력·거부된 승인은 상태를 바꾸지 않는다.
- 파일 복사 뒤 기록 append에 실패하면 사본만 남을 수 있다. 사본은 정본이 아니며
  재시도는 검증된 동일 바이트 사본을 재사용한다. 기록 append가 결과 등록의 완료 지점이다.
- 현재 자산 상태를 모델 payload에 전달한다. 연결된 자산의 버전/내용 변경과
  커밋 뒤 새 연결은 원고의 재검사 사유가 된다. 원고 본문은 자동 수정하지 않는다.
  자산 재검사 사유는 최신 원고 재검사의 refs를 기준으로 해소한다.

## 구현 순서와 파일 책임

1. `core/assets/`에 파일 인계·입력 규약·기록 재생·상태 조회·쓰기·검토/결정을 분리한다.
   파일별 300줄 이하. 정본은 하나, 파생 상태는 매 호출 계산한다.
2. 기존 `core/store/assets.js`가 YAML과 관리 자산을 합쳐 읽는다. 동일 ID 충돌은 거부한다.
   원고 scope/payload/status와 자산 변경 재검사 표시를 연결한다.
3. 서버는 공개 core 함수만 호출하는 `folio_assets` 처리기를 추가한다.
4. Folio 스킬에 호스트 생성 → 공통 등록 → 검토 → 작가 결정 흐름을 넣는다.
   특정 제공자의 호출 명령은 넣지 않는다. 사람용 문서와 그림책 안내를 실제 구현 범위로 갱신한다.
5. 합성 파일과 가짜 호스트로 실패·변경·승인 및 실제 stdio MCP 흐름을 검증한다.
6. 각 계획 항목을 코드/실행 증거에 대응시켜 수용 결과를 아래에 기록한다.

## 수용 검증표

| 항목 | 필수 증거 |
|---|---|
| 제공자 독립 | 제공자 ID 유무와 임의 origin이 같은 공통 도구로 처리됨; core/packs 네트워크 가드 |
| 생성 없는 호스트 | 설명서만 등록·조회 가능; 생성 완료·승인으로 오인하지 않음 |
| 공통 인계 | 파일 복사/hash/원본 삭제 뒤 사용 가능; URI 무다운로드·승인 불가 |
| 버전·승인 | 교체/설명서 변경/새 검토 뒤 옛 승인 미적용; 오래된 expectedRev/reviewId 거부 |
| 잠금 | hard/block/advisory, 자기검토, 내용 변경·손실, 잘못된 입력의 비변경 |
| 정본 무결성 | 기록 변조·중간 실패·사본 재시도·링크/경로/용량·동시 갱신 거부 |
| 작품 연결 | 사용 위치, 모델 재료, 변경/새 연결 뒤 stale, 재검사 뒤 해소, 본문 비자동수정 |
| 호스트 프로토콜 | 실제 stdio MCP 등록 → 인계 → 검토 → 승인 → 교체 → 재검토 → 재승인 |
| 기존 호환 | 기존 YAML fixture, 기존 전체 테스트·합성 예제·새 설치 |
| 지침 일치 | 스킬/문서가 생성 주체와 등록 형식·현재 한계를 정확히 설명함 |

이미지 팩의 별도 생성 파이프라인, 제공자 SDK, 외부 다운로드, 지면 제작은 이번 구현에서
필요하지 않다. 실제 이미지 도구와의 수동 실습 및 시각 검토 정확도는 자동 테스트와 구분해 보고한다.
