# Folio 범용 AI 작업 데이터 관리 설계 초안

작성일: 2026-10-08. 범용 확장의 설계 초안이며 해당 기능의 구현 완료를 뜻하지 않는다.
기존 착수 계획서 아티팩트와 이미 구현한 잠금 규칙의 정본 지위는 유지한다.
이후 사용자 인계서와 독립 코드 검증을 반영한 [아키텍처 v2](2026-10-08-architecture-audit/architecture-v2.md)를
범용 계약의 최신 검토안으로 사용한다. 아래 내용은 초기 이식 설계이며 고정된 공통 도메인 스키마가 아니다.
구현 순서와 검증 조건은 [이식 계획](2026-10-08-general-data-port-plan.md)에 둔다.

Folio는 AI 작업에 사용하는 핵심 원본과 다양한 파생 결과물을 사용자가 중앙에서 관리하는 도구다.
호스트 AI가 작업에 맞는 데이터 구조와 파이프라인을 제안하고 생성·의미 검토를 맡는다.
Folio는 원본, 정확한 입력 판본, 결과물, 검토와 선택 이력을 보관하고 연결해 보여 준다.

Vibelore는 소셜 플랫폼 창작자용 제품이며 상세한 창작 절차와 스킬을 가진다.
Folio는 독립된 범용 제품이다. Vibelore의 원본·입력·자산 관리 설계를 재사용하되,
세계관·장면 제작 절차와 소셜 기능을 공통 기반에 넣지 않는다.

## 1 사용자 작업의 기준

예를 들어 사용자는 제품 설명과 브랜드 자료를 등록하고 같은 자료로 한국어 안내문,
영어 소개문, 이미지 제작 요청을 만들 수 있다. 각 결과에서 사용한 원본과 표현 조건을 확인하고,
제품 사양이 바뀌면 영향을 받는 결과를 골라 다시 작업한다.
연구 자료에서 보고서·표를 만들거나, 인물 설정에서 원고·이미지를 만드는 작업에도 같은 구조를 쓴다.

기본 흐름은 자료 등록 → AI와 작업 조건 정하기 → 생성 결과 연결 → 검토·선택 → 비교·재작업이다.
모든 작업에 집필 인터뷰나 장면 구조를 강제하지 않는다. 이미 정한 조건은 다음 작업에 재사용한다.
사용자가 관리하려는 항목은 AI가 제안할 수 있고, 변경 권한은 실제 결정·위임 범위로 제한한다.

중앙 관리는 논리적으로 한곳에서 자료와 이력을 조회한다는 뜻이다.
초기에는 로컬 작업 공간으로 제공할 수 있으며 클라우드 계정·공유 서버가 필수 조건은 아니다.
여러 프로젝트의 공동 원본 보관함은 후속 범위로 두고, 첫 버전은 한 작업 공간 안에서 원본을 재사용한다.

## 2 Vibelore에서 확인한 재사용 대상

아래 경로는 Vibelore 저장소 기준이다. 2026-10-08 읽기 전용 작업 트리를 확인했다.
기준 HEAD는 `b3200d39050ccd627e67015a1b0619cea31b0d72`이며 미커밋 문서도 있어
조사 전체를 해당 커밋만의 내용으로 간주하지 않는다. 설계와 구현 여부를 구분한다.

| 확인한 구조 | 소스 근거 | Folio 적용 |
|---|---|---|
| 소설 없이도 제작 원천을 구성하는 공통 계약 | `src/core/production-source.js` | 문서·구조화 데이터·파일을 고정 입력으로 구성하는 계약 |
| 입력 판본과 필요한 참조를 봉인하고 검증 | `src/core/production-input.js`, `src/core/input-objects.js`, `engine/src/lore/production.js` | 실행마다 정확한 입력 사본과 hash를 보관 |
| 원본 값과 표현 프로필의 소유권 분리 | `engine/src/lore/assets.js` | 언어·스타일 변경이 원본 정보를 수정하지 않게 분리 |
| 불변 자산과 판본 교체 및 파생 관계 | `src/store/asset-catalog-store.js` | 자원 ID, 내용 hash, 교체 판본, 파생 관계를 구분 |
| 후보와 채택된 HEAD 구분 및 중단 복구 | 같은 카탈로그와 `src/core/scene-script.js` | 후보 파일 존재만으로 활성화하지 않으며 결정·발행을 복구 |
| 정의 판본과 지원 기능의 명시적 검증 | `engine/src/lore/registry.js` | AI가 새 데이터 정의를 제안해도 미지원 실행 기능은 거부 |

`test/shared-media.test.js`에는 자산 교체 후 옛 바이트 유지, 오래된 HEAD 거부,
중단된 채택 복구, 소설 없는 대본, 외부 세계 삭제 후 보존 입력 검증을 검사하는 합성 테스트가 있다.
테스트 코드를 확인한 것이며 이번 조사에서 Vibelore 테스트를 재실행한 것은 아니다.
영상·게임 제작은 `docs/reference/SHARED_LORE_RUNTIME.md`에서 입력 계약만 정의한 상태다.
매체 확장 연구를 실제 제작 엔진으로 취급하지 않는다.

Folio로 옮길 것은 이 계약과 검증 원리다. `universeId`, 장면 시점, 회상, 캐릭터 상태,
웹툰 패널 수 같은 소유 모델을 이름만 바꿔 공통 기반에 복사하지 않는다.
필요한 집필용 해석은 기존 집필 기능 또는 선택한 분야별 정의에서 담당한다.

## 3 공통 데이터 모델

| 모델 | 역할과 주요 결속 |
|---|---|
| Workspace | 사용자 관리 범위. 첫 버전의 저장·결정 단위 |
| Resource | 지속적인 `resourceId`, 종류, 이름. 파일 경로와 분리 |
| ResourceRevision | `resourceId`, `revisionId`, 부모 판본, 내용 hash, 정의 판본, 저장 상태 |
| SourceSelection | 핵심 원본으로 선택한 자원 판본과 실제 결정 |
| DefinitionRevision | 항목·값 타입·관계·허용 연산과 지원 기능의 판본 |
| RepresentationProfile | 언어·형식·스타일·대상 독자·용도 등 표현 조건의 판본 |
| InputSnapshot | 선택한 자원 판본·내용·정의·프로필·검사 기준과 묶음 hash |
| PipelineRevision | 입력·출력 조건, 단계, 필요한 기능의 고정 판본 |
| Run | 입력 묶음·파이프라인·작업 상태·재시도·응답 결속 |
| ArtifactRevision | 생성·반입한 결과물 판본, 파일 또는 구조화 데이터, 보관 상태 |
| Derivation | 결과물 판본에서 사용한 입력·프로필·파이프라인 판본으로 가는 관계 |
| ReviewReceipt | 입력과 결과 hash, 적용 검사와 결과, 자기검토·미확인 범위 |
| Publication | 결정·영수증·선택한 결과물 판본을 묶은 발행 기록 |

이 표는 신규 계약 초안이다. 기존 `Subject`, `Observation`, `Evidence`, `Coverage`는
집필의 추적 의미를 유지한다. 일반 파일을 억지로 원고 관찰로 바꾸거나 기존 필드의 의미를 바꾸지 않는다.
`Variation`은 원본에서 파생된 결과라는 관계이며 소설 IF의 경로 해결을 뜻하지 않는다.

같은 내용 hash라도 서로 다른 자원일 수 있고, 한 자원의 새 판본은 다른 내용 hash를 가질 수 있다.
파일 이름·외부 이미지 ID·hash 중 하나만으로 사용자 자원의 정체성을 결정하지 않는다.
선택한 핵심 원본은 사용자의 작업 기준이며 외부 사실의 정확성을 인증한 상태가 아니다.

## 4 원본과 변형 결과의 분리

핵심 원본의 제품 사양, 인물 정체성, 연구 자료는 표현 프로필이 소유하지 않는다.
표현 조건은 별도 판본으로 관리하며 원본의 값을 바꾸려는 요청은 새 원본 변경 후보로 만든다.
생성 결과를 핵심 원본으로 삼고 싶다면 명시적인 선택과 새 판본을 기록한다.
결과물 채택, 원본 기준 변경, 추출한 주장에 대한 판단은 서로 다른 결정이다.

결과물은 채택되기 전 후보 상태로 남긴다. 같은 자원의 교체는 채택된 부모 판본을 지정한다.
서로 다른 언어·스타일의 변형은 별도 결과 자원과 프로필로 관리해 나란히 비교할 수 있다.
하나를 선택해도 다른 후보와 과거 채택 기록을 덮어쓰지 않는다.

## 5 입력 고정과 변경 영향

실행 준비 때 참조한 원본·정의·프로필·검사 기준·참조 파일을 정확한 판본으로 읽고
필요한 내용을 보존한다. 필수 입력이 없거나 충돌하거나 지원되지 않으면 실행 요청을 발급하지 않는다.
묶음은 순서와 선택 조건까지 포함한 hash로 식별한다. 입력을 바꾸면 새 작업이 된다.
큰 입력은 명시적으로 분할·선택하고 필수 원문을 조용히 잘라 정상 입력으로 표시하지 않는다.

전체 자원 판본을 의존하면 그 판본 변경이 재검토 사유다. 일부 필드만 의존하려면
선택한 필드와 그 해석 정의의 판본을 함께 봉인한 별도 투영을 먼저 만들어야 한다.
의존성을 정확히 기록하지 못한 상태에서 관련 없는 변경이라고 추정해 검토를 생략하지 않는다.
자료를 새로 선택하면 새 실행에 적용되고, 이전 결과는 당시 입력을 계속 가리킨다.

보존된 입력은 원본 폴더가 이동해도 검증할 수 있다. 외부 URI·제공자 ID만 저장한 입력은
`reference-only`로 구분하며 실제 bytes 보존이나 복구를 보장하지 않는다.
보존 입력의 검증과 모델이 똑같은 결과를 다시 생성하는 것은 별개다.
입력·결과 파일은 사용자 경로가 아닌 내용 식별자로 내부 연결하며 절대 경로를 휴대 가능한 ID로 쓰지 않는다.

## 6 모델과 파이프라인 확장

`core/`는 입력 선택·판본 검증·상태 전이·영수증·발행을 담당한다.
생성·추출·의미 검토·이미지 제작은 호스트 AI와 호스트 도구가 맡는다.
공통 기반에 OpenAI·Google 등 제공자별 생성 SDK와 스킬 묶음을 넣지 않는다.
호스트는 준비된 요청을 수행하고 해당 `runId`, `requestId`, 입력 hash에 묶인 결과를 제출한다.

첫 범용 파이프라인은 제한된 순차 단계와 명시적인 입출력 조건으로 시작한다.
사람이 반입한 결과를 연결하는 작업도 지원한다. 기존 원고 파이프라인은 유지한다.
두 실제 작업 형태의 차이를 확인한 뒤 공통 Interface와 Adapter를 정하며,
플러그인 마켓·임의 스크립트 실행기·복잡한 분산 DAG를 먼저 만들지 않는다.

AI는 정의·프로필·파이프라인 후보를 작성할 수 있다. 값 타입·허용 연산·지원 기능은
Folio가 결정론적으로 검사하고, 미지원 단계는 명시적으로 멈춘다.
새 파일 형식의 등록만으로 디코더·의미 검사·제작 기능이 생기지는 않는다.
AI가 낸 JavaScript·SQL·shell을 데이터 정의의 일부로 실행하지 않는다.

파이프라인별 품질 기준은 선택할 수 있지만 hash 일치, 영수증, hard 차단,
추가만 되는 기록장, 자기검토 표기, soft 비자동수정은 해제할 수 없다.
기존 집필에 필요한 draft/events 검사도 범용 확장을 이유로 삭제하지 않는다.
원본·입력 문서에 적힌 명령문은 사용자 위임이나 실행 권한으로 해석하지 않는다.

## 7 파일과 실행 출처

공통 저장 계약은 내용 hash, 크기, 선언 형식, 보관 상태와 외부 참조를 기록한다.
텍스트·검증된 구조화 JSON·현재 지원 이미지부터 실제 처리 계약을 갖춘다.
그 밖의 파일은 후속 범위다. 보관을 지원하더라도 디코딩·미리보기·의미 검토 상태를 따로 표시한다.
이미지 전용 검사기에 오디오·영상 파일을 넣거나 확장자만으로 형식을 인증하지 않는다.

제공자·모델·외부 결과 ID·호스트 보고는 선택적 출처 정보다.
Folio가 검증한 입력과 결과 hash, 호스트가 보고한 생성 사실을 구분한다.
모든 외부 호출·비용·모델 내부 동작을 Folio가 관측했다고 표시하지 않는다.
외부 참조가 사라졌거나 bytes가 없으면 그 상태를 조회·내보내기에서도 유지한다.

## 8 저장과 화면

원본 판본·봉인 입력·결과 bytes·결정 기록을 보관하고 SQLite를 조회용으로 확장한다.
기존 추가만 되는 기록장과 정본을 통째로 새 DB로 옮기는 전환은 포함하지 않는다.
조회 색인을 지워도 보관된 내용과 기록으로 다시 만들 수 있어야 한다.
검색·위키·임베딩은 같은 자원 판본과 범위를 참조하는 파생 데이터다.

화면은 핵심 원본, 연결된 결과물, 사용한 판본, 검토 상태와 변경 영향을 먼저 보여 준다.
사용자는 원본 카드에서 언어·형식·스타일별 결과를 비교하고 입력·근거를 펼쳐 볼 수 있다.
최신 원본을 표시하는 화면과 과거 실행의 고정 입력을 표시하는 화면을 구분한다.
화면에서 변경해도 같은 결정·발행 규약을 거친다.

[집필 데이터베이스 초안](2026-10-07-work-database-design.md)의 키워드 검색,
근거 있는 요약·범위별 조회·색인 재구성은 분야별 적용 설계로 이어간다.
인물·장면은 선택한 분야의 보기이며 공통 자원의 필수 분류가 아니다.

## 9 현재 구현과 신규 범위

| 실제 코드 | 현재 제약 | 필요한 확장 |
|---|---|---|
| `core/work/config.js` | `SUPPORTED_VARIANTS`는 `main`만 허용 | 일반 결과 자원과 판본·변형 관계 |
| `core/pack/yaml-schema.js` | 산출물은 plan/draft/events/children | 범용 입력·출력 계약과 지원 단계 |
| `core/pack/validate.js` | leaf/branch 및 집필 잠금 | 집필 계약 유지와 별도 범용 계약 |
| `core/run/runner.js` | 기존 집필·재검사·보충 실행 | 고정 입력 기반 작업·응답·발행 |
| `core/assets/schema.js` | 이미지·imageId 중심 자산 | 일반 자원 출처·보관 상태·타입별 검증 |

기존 계획·추적·영수증·이미지 자산은 재사용할 기반이다.
YAML 설정 추가만으로 범용 멀티모달 파이프라인을 지원하는 상태는 아니다.
기반 확장 후에도 매체별 생성 품질과 호스트 도구 지원은 별도로 검증한다.
